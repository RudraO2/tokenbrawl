# Story 12.7 — Best of three, and a fight that ends with something on the screen

As a visitor, I want a fight to be a best-of-three set that ends with a KO or a TIME OVER on screen, so that a Match finishing is an event rather than a canvas that stops moving.

## The gap, measured

`packages/env-fighter/src/config.ts`: `maxTicks: 1200`, `ticksPerDecision: 30`. One Match is one round of roughly forty Decision Points per Agent, and there is no round system anywhere in the repository — no round counter, no set, no between-round state.

And a Match mostly does not end in a KO. Every committed log under `apps/web/public/replays/`, read on 2026-08-10:

| Log | `result.endReason` |
|---|---|
| `demo.command-log.json` | `timeout` |
| `spectate-01` | **`ko`** |
| `spectate-02` | `timeout` |
| `spectate-03` | `timeout` |
| `spectate-04` | `timeout` |
| `spectate-05` | `timeout` |
| `spectate-06` | `timeout` |

**Six of seven end in `timeout`.** (The epic brief said five of seven; the count above is what the files actually contain.) So the overwhelmingly common way a visitor sees a fight end is: the fighters stop, and nothing says why. `spectate-01`'s KO is equally silent — there is no KO overlay to draw.

Story 12.6 drew the round pips and had nothing to count. This story is what they count.

## The design decision this story turns on, and it is not optional

**A round is a Match. A set is three Matches. The simulation is not touched.**

The tempting version — a `roundsPerMatch` in `FighterConfig`, health reset between rounds, one Command Log covering the set — is wrong three times over, and each way is a stop-and-escalate:

1. **`docs/contracts/command-log.schema.json` and `command-log.v2.schema.json` are FROZEN.** There is no round field and none may be added. A Command Log is one Match.
2. **Adding any field to `FighterConfig` changes `configHash`**, which is recorded in every committed log. Every one of the seven above would stop verifying.
3. **Changing `maxTicks`, health or the round structure changes every Final-State Hash in the repository** and re-opens the Story 2.4 and 8.5 skill-separation gates. This is a presentation epic. It re-runs no gate.

So: an arcade **session** runs three Matches back to back, each a full unmodified Match with its own Command Log and its own hash, with seeds derived deterministically from the session seed. The first side to win two Matches wins the set. The pips count Matches won. Nothing in `packages/` is edited, no committed log is invalidated, no gate is re-opened, and a visitor sees best-of-three.

A round's winner is read from the log's existing `result`: `outcome` names the side, `endReason` is `ko` or `timeout`, `healthRemaining` breaks a timeout tie. All three fields already exist and are already populated.

## The overlays

Two, both drawn in the arena by the existing HUD vocabulary:

- **`K.O.`** when `endReason` is `ko`, over the losing fighter's side.
- **`TIME OVER`** when `endReason` is `timeout`, centre screen, followed by which side is ahead on health.

Then the set state: `ROUND 2`, or `YOU WIN` / `YOU LOSE` when a side reaches two. These are `arcadeText` callouts, drawn for a **counted** number of frames — never a `setTimeout`, which `source-discipline.test.ts`'s wall-clock sweep bans and which would make the overlay's length depend on the machine.

## Acceptance criteria

**Given** a visitor who has won or lost a round, **When** the round ends, **Then** an overlay is drawn on the arena naming the ending — the check `match-end-overlay`, added to `scripts/visual-gate.mjs` by this story, which scrubs `#app` to the demo log's final frame and requires ink in the centre overlay band that is absent at frame 0.

**Given** a round won, **When** the HUD redraws, **Then** the winning side's next pip is filled, **and** `hud-round-pips-advance` passes with its entry deleted from `docs/visual/known-failures.json`.

**Given** a visitor in an arcade session, **When** a round ends and neither side has two wins, **Then** the next round starts on the same screen with health restored, the pips retained and the fighters unchanged. No return to a menu between rounds.

**Given** a side reaching two wins, **When** the set ends, **Then** the set result is drawn and the visitor is offered a rematch and a return to character select, both keyboard-reachable with the `--tb-accent` focus outline.

**Given** a completed session, **When** its logs are inspected, **Then** there are up to three Command Logs, each a valid unmodified `CommandLogV2`, each verifying its own Final-State Hash, and each with the `agentIdentity.kind: "human"` that keeps an Arcade Match out of the ratings (AD-14).

**Given** the same session seed and the same inputs, **When** the session is replayed, **Then** the same three seeds are derived and the same three logs are produced. A set is as deterministic as a Match.

**Given** every previously committed Command Log, **When** verified, **Then** its hash is unchanged and `configHash` still matches. This is the AC that proves the design decision above was actually honoured.

**Given** a visitor with `prefers-reduced-motion: reduce`, **When** an overlay draws, **Then** it appears without animating in, and its counted hold is unchanged.

## Scope

`apps/web/src/arcade/panel.ts` and a new session module beside it (the three-Match sequence and the pip state), `apps/web/src/render/hud.ts` and `apps/web/src/render/renderer.ts` (the overlays and the pip fill), `apps/web/src/render/arena-palette.ts` if an overlay needs a colour, `scripts/visual-gate.mjs` (`match-end-overlay`), `docs/visual/known-failures.json` (delete `hud-round-pips-advance`).

**Explicitly not in scope, and a stop-and-escalate if it looks necessary:** anything under `packages/`, `docs/contracts/`, or `apps/web/public/replays/`.

## Frozen contracts touched

None, and this story is the one in the epic most likely to think it needs to. `command-log.schema.json` and `command-log.v2.schema.json` are frozen; a round is not a Command Log concept and must not become one. If a round system appears to require a schema field or a `FighterConfig` key, **stop and escalate** — the answer is the session model above, and if that is genuinely insufficient the decision belongs to the owner, not to a dev session.

## Invariants at risk

- **INV-1** — an overlay's duration is a counted number of frames. No timer, no `setTimeout`, no `performance.now()`.
- **INV-2** — three deterministic Matches, three replayable logs.
- **AD-14** — every Match in the session is human-vs-bot and excluded from rating.
- **AD-15** — presentation and session orchestration only.

## Two regimes

The overlays are drawn in `apps/web/src/render/**/*.ts` and get the arena's release. The rematch and menu controls are **page chrome** and keep every `docs/DESIGN.md` rule. Canvas text answers to the 4.5:1 floor and its measured ratio is recorded here.

## Test plan

- The session derives three seeds deterministically and stops at two wins (a 2–0 set runs two Matches, not three).
- A round's winner is read from `result` and matches an independent reading of `healthRemaining`.
- The overlay's frame budget is counted, asserted by advancing the clock rather than by waiting.
- Each committed Command Log still verifies, asserted over the whole `apps/web/public/replays/` directory.
- Pips reflect wins for every set score.

## Exit gate

`npm test` green **AND** `bash scripts/audit-invariants.sh` exiting zero **AND** `node scripts/visual-gate.mjs` exiting zero with `match-end-overlay` passing and `hud-round-pips-advance` passing **unwaived**.
