# Story 12.2 — Play vs CPU draws the fight while you are playing it

As a visitor who clicked Play vs CPU, I want to see the fight I am playing, so that pressing a key is a fighting game rather than a form submission.

**This is the most damaging defect in the audit and it goes first after the gate.** Every story below it changes something about how a Match looks, and until this one lands, one of the three surfaces cannot show any of it.

## The gap, measured

`apps/web/src/arcade/run.ts` states it in its own docblock, at the `onLegalActions` field:

> *"An Arcade Match runs **headlessly** (`startup.ts` re-mounts the player only once it has finished), so while a visitor is playing there is no canvas and therefore no Super Gauge on screen."*

That comment exists because Story 10.6 hit the wall and worked around it: it added a callback so the DOM panel could print "your bar is full" in text, because there was no gauge to light up. The workaround was correct for that story and it is the wrong shape for the product.

Verified live by Story 12.1's gate run on 2026-08-10: with the page loaded and `Play vs CPU` clicked, the document holds **exactly two canvases**, one under `#app` and one under `#spectate`, and **none under `#arcade`**. The `#arcade` capture shows the section's status line reading "Fighting." above empty page. `arcade-live-canvas` is waived in `docs/visual/known-failures.json` naming this story.

The cause is structural, not a missing element. `runArcadeMatch` returns a `Promise<CommandLogV2>` and `startup.ts` awaits it, then calls `mount()` → `renderApp` → `mountPlayer` on the finished log. The Match is a computation that yields a replay. Nothing draws during it because there is nothing to draw from until it is over.

## What "renders while you play" has to mean here

The player already knows how to draw a Match: `buildReplayFilm` turns a Command Log into frames and `drawJuicedFrame` draws one. What it cannot do is draw a Match that has not finished. So the work is to give the arcade a **live** frame source — a fighter-state pair per Decision Point, drawn as it is produced — without forking a second renderer.

Three constraints bound the shape, and none of them is negotiable:

- **`drawFrame` and `drawJuicedFrame` are reused, not reimplemented.** A second drawing path is how Story 9.3's Spectate panel ended up on coloured blocks while the player beside it ran the full art. If this story finds itself writing `ctx.drawImage`, it has gone wrong.
- **No clock may enter the simulation.** `runMatch` and `createFighterEnvironment` are untouched (AD-14, INV-1). The live frame source observes; it does not pace. `source-discipline.test.ts`'s wall-clock sweep and `deltaTime` ban still apply, and the frame the arcade paints is chosen by counting callbacks exactly as `player/clock.ts` does.
- **The Final-State Hash of an Arcade Match does not change.** Whatever this story adds is a read, and `arcade/log.test.ts`'s existing assertions must still hold byte for byte.

The completed Match still re-mounts the player afterwards. A visitor who just fought gets the replay with hover reasoning, exactly as today — this story adds the live view in front of it, it does not remove the replay behind it.

## Acceptance criteria

**Given** a visitor who has clicked `Play vs CPU`, **When** the Match starts, **Then** a visible canvas exists under `#arcade` for the whole time the Match is running, **and** `arcade-live-canvas` passes with its entry deleted from `docs/visual/known-failures.json`.

**Given** that canvas, **When** the visitor presses `ArrowRight` thirty times, **Then** the canvas's pixel hash changes between the first press and the last — the check `arcade-input-moves-fighter`, added to `scripts/visual-gate.mjs` by this story, which drives the keys through real `keydown` events on the page rather than by calling into the panel.

**Given** that canvas, **When** the gate samples it, **Then** `canvas-not-blank` holds for it as it already does for `#app` and `#spectate`: at or above 2% ink, drawn with the sprite artists and the backdrop, not the block-artist fallback. The existing check already sweeps every canvas on the page, so this AC costs no new check — it costs this story getting the dressing wired the way `startup.ts` wires it for the player.

**Given** the Match ending, **When** the log is built, **Then** the replay player re-mounts on it exactly as it does today, and the live canvas gives way to it rather than both being on screen at once.

**Given** the same seed, the same bot and the same key sequence, **When** the Match is run twice, **Then** the Command Log and its Final-State Hash are byte-identical to what this code produced before the story. Drawing a Match must not change it.

**Given** a visitor with `prefers-reduced-motion: reduce`, **When** they play, **Then** the arena still draws — the preference reduces the picture (no shake, no particles) exactly as `buildJuiceTrack` already handles it, and never removes the fight. Story 11.6's third pass is the precedent: porting a "do not animate" policy onto a surface with no transport produced a dead surface, not an accessible one, and the arcade's transport is the visitor's own hands.

**Given** the console, **When** the Match runs and finishes, **Then** `console-clean` still passes. The asset loaders warn rather than throw, so a pack that failed to reach the new canvas reports itself there and nowhere else.

## Scope

`apps/web/src/arcade/panel.ts`, `apps/web/src/arcade/run.ts` (the live-frame tee only — the Match composition is not touched), `apps/web/src/startup.ts` (dressing the arcade surface the way it already dresses the player), `apps/web/src/styles/` (the panel's canvas box), `scripts/visual-gate.mjs` (the new `arcade-input-moves-fighter` check), `docs/visual/known-failures.json` (delete `arcade-live-canvas`).

Not in scope: `packages/**` of any kind, `apps/web/src/render/**` (this story reuses the renderer, it does not change it), the camera (Story 12.3), the HUD's missing elements (Story 12.6).

## Frozen contracts touched

None. `docs/contracts/index.ts` and both `command-log*.schema.json` are untouched. If a live frame source appears to need a change to `EnvironmentAdapter` or to `MatchResult`, **stop and escalate** — it does not, because the states this story draws are the states `runMatch` already produces.

## Invariants at risk

- **INV-1** — no wall clock may reach the simulation. The live view counts frames; it does not measure them.
- **INV-3** — a viewer must not be able to tell how long an Agent took. A live arcade view against a Baseline Bot has no thinking time to leak, but the frame cadence must stay a fixed count per Decision Point regardless, because the same path will later show a Deployment.
- **AD-14** — `createHumanAgent` stays the one place an input becomes an Action. A renderer that reads keys is a second clamp.

## Two regimes

`apps/web/src/render/**/*.ts` is the arena and is released from the three colour and compositing rules. The `#arcade` panel itself is **page chrome** and keeps every rule in `docs/DESIGN.md`: 3–4px `--tb-ink` borders, `6px 6px 0` hard shadow, zero radius, flat fills, no translucency. Read the "Two regimes" section before styling the canvas's frame.

## Test plan

- The arcade panel mounts a canvas before the Match's first Decision Point resolves, asserted against a recording fake with no DOM.
- The live frame source emits the same call sequence `drawJuicedFrame` produces for the equivalent replay frame.
- A Match run headlessly and the same Match run with the live view produce identical Command Logs and identical Final-State Hashes.
- Reduced motion draws a reduced picture and a live one.

## Exit gate

`npm test` green **AND** `bash scripts/audit-invariants.sh` exiting zero **AND** `node scripts/visual-gate.mjs` exiting zero with `arcade-live-canvas` passing **unwaived** and `arcade-input-moves-fighter` passing. A run that passes only because the waiver is still in the file is a failed story: the gate now fails on a stale waiver, so leaving it behind cannot be missed.
