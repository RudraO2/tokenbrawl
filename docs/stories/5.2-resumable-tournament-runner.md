# Story 5.2 — Resumable tournament runner

As the developer, I want a tournament that survives being killed halfway, so that free-tier quotas spread across five days instead of forcing everything into one impossible run.

## Acceptance criteria

**Given** a tournament killed at match 40 of 200, **When** it is restarted, **Then** it completes only the 160 outstanding Matches and re-runs none of the first 40.

**Given** resumption, **When** the runner determines what is outstanding, **Then** it derives that from the set of already-committed Command Logs — **not** from a separate state file, database, or queue.

**Given** a provider hitting its daily quota, **When** the runner detects it, **Then** it parks that Deployment's remaining Matches and continues with other Deployments rather than failing the run.

**Given** rate-limit responses, **When** they occur, **Then** the runner backs off and sleeps between calls; the adapter itself holds no quota state.

**Given** any single CI job, **When** it is written, **Then** it does not assume it completes the tournament in one run.

## Scope

`packages/cli` or a runner module: scheduling, quota bookkeeping, backoff, and resume logic.

## Frozen contracts touched

None modified.

## Invariants at risk

- **INV-8** — the resume mechanism must not become a database. Committed logs are the store.

## Architecture decisions that constrain this

- **AD-9** — quota and backoff state live here, not in adapters; resumable state IS the committed logs.
- **AD-8** — `matchId` derivation must be stable, or resumption will re-run completed Matches.

## Test plan

Kill-and-resume at several points. Quota-exhaustion parking. Backoff on simulated 429s. A test asserting no separate state store is written.

## Exit gate

`npm test` green **AND** `bash scripts/audit-invariants.sh` exiting zero. Reviewer opinion is never a gate.
