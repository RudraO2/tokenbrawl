# Story 4.3 — Hover a fighter to see its reasoning

As a visitor, I want to see what a model was thinking at the moment it acted, so that the benchmark shows me its reasoning instead of only a score.

**This is the centrepiece feature. Build the layout around it rather than bolting it on.**

## Acceptance criteria

**Given** playback at a given position, **When** a visitor hovers a fighter, **Then** the reasoning shown is for the Decision Point at that exact position — not the nearest neighbour.

**Given** a Decision Point served in Reflex Mode, **When** hovered, **Then** it displays as such rather than showing blank reasoning.

**Given** a Decision Point that was a Parse Failure, **When** hovered, **Then** it says so and shows the raw response.

**Given** a touch device, **When** a visitor taps a fighter, **Then** the same reasoning appears.

**Given** keyboard navigation, **When** a fighter receives focus, **Then** the reasoning is reachable and exposed to screen readers.

## Scope

`apps/web`: hover, tap and focus interaction, reasoning panel, and the layout that makes it the visual centre.

## Frozen contracts touched

None modified.

## Invariants at risk

- **INV-3** — the reasoning panel must not display or imply response latency.

## Architecture decisions that constrain this

- **AD-10** — reasoning may arrive late; handle the not-yet-loaded state.

## Test plan

Exact Decision-Point correspondence at several playback positions, including boundaries. Reflex-Mode and Parse-Failure display states. Touch and keyboard reachability. Screen-reader exposure. Visual verification via the Chrome DevTools MCP.

## Exit gate

`npm test` green **AND** `bash scripts/audit-invariants.sh` exiting zero. Reviewer opinion is never a gate.
