# Story 9.2 — Human-vs-Baseline-Bot local arcade match

As a visitor, I want to play a Baseline Bot myself, so that I'm participating in thirty seconds instead of only watching.

**Does not depend on Epic 8.** Runs against whichever engine exists — nothing here reads Zone, jump, or Juggle Count.

## Acceptance criteria

**Given** a visitor selects Play-vs-CPU, **When** the Match starts, **Then** they control one side, submitting Actions through the same grammar any Agent uses.

**Given** visitor input (keyboard or touch), **When** it is captured, **Then** it maps only to legal Action-grammar values before reaching the Environment — no raw key or frame is ever read by simulation code directly (AD-14).

**Given** a human-controlled Match, **When** it runs, **Then** it uses the existing Environment/Harness completely unchanged — no forked "arcade" simulation path exists anywhere.

**Given** the resulting Command Log, **When** entries are written for the human side, **Then** `agentIdentity.kind` is `"human"` (Story 8.1's schema addition) and zero tokens are consumed or reported — unmetered, the same as a Baseline Bot.

**Given** that Command Log, **When** rating computation runs over any corpus containing it, **Then** the Match is excluded, per AD-14.

**Given** the resulting Command Log, **When** played back later, **Then** it is valid and playable in the same replay player as any other Match — no special-cased player path.

## Scope

`apps/web` only: input capture and mapping, and a new `Agent`-port implementation (per `docs/contracts/index.ts`) whose `decide()` reads UI state instead of calling a provider. Lives beside the existing `DeploymentAgent`/Baseline Bot implementations conceptually, but in `apps/web` rather than `packages/providers` or `packages/env-fighter` — a human is a presentation-layer concern, not a simulation or provider concern.

## Frozen contracts touched

None. The `Agent` port already accepts any `decide()` implementation; this story adds one, it does not change the interface.

## Invariants at risk

- **INV-1** — no change needed here: the blocking-agent-interface design (FR-5) already tolerates arbitrary response time by construction. A human thinking for ten seconds is not a special case, it's the case the harness was already built for.
- **INV-7** — does not apply to a human the way it applies to a Deployment. INV-7 governs Scaffold byte-identity *across Deployments*; a human never receives the text Scaffold at all, they see the rendered game. Note this explicitly in review so nobody tries to force a text prompt in front of a human player to satisfy a rule that was never about them.
- **INV-4** — a human Agent has no Token Bank interaction at all, the same as a Baseline Bot.

## Architecture decisions that constrain this

- **AD-1** — `packages/core` stays pure; the human `Agent` implementation lives entirely in `apps/web`.
- **AD-14** — this story is AD-14's implementation: Agent-shaped human input, `kind: "human"`, unmetered, excluded from rating.

## Test plan

Unit test: out-of-grammar or malformed input never reaches the Environment (clamped or rejected at the mapping boundary). Integration test: a scripted sequence of button presses runs a full human-vs-bot Match headless, producing a valid Command Log with `kind: "human"` and zero token fields. Live check via the Chrome DevTools MCP: a full Match is playable start to KO in the browser with no key and no network call beyond the initial page load.

## Exit gate

`npm test` green **AND** `bash scripts/audit-invariants.sh` exiting zero **AND** the live browser check passing.
